# space_live_project 音效與角色聲音模組重構計畫書

## 重構背景與目標
space_live_project 在 `feature/sound_effcets` 分支中針對音效和角色語音處理遇到結構上的挑戰。當前實作中，**音效管理 (SoundEffectManager)** 與 **角色語音模組 (TTS/Singing)** 的職責混淆，導致系統維護和擴充困難。此外，播放音效的流程需要更明確的前後端分工，目前有部分邏輯在後端處理播放，缺乏彈性。為了解決這些問題，我們將進行全面重構，具體目標如下：

- **模組分離：** 明確區分並重構「音效」與「角色聲音」兩大模組。也就是將純音效（背景音、效果音）相關的邏輯與角色語音（TTS 文字轉語音與唱歌聲音）相關的邏輯分離，避免彼此耦合。
- **前端主導播放：** 所有音效/語音的播放流程將由前端主導。也就是先由後端提供結構化的播放指令（例如定義好的 API JSON 格式），由前端進行解析、驗證與排程後再實際播放。後端不直接控制播放器，而是提供**什麼**播放及**何時**播放的資訊。
- **兩組聲音播放管線：** 將音效與角色語音拆成兩組播放管線各自運作：  
  - *音效管線：* 包含背景音效、音樂片段、特定組合音效（Combo）、Tone.js 即時合成音效，以及來自 FreeSound 的快取音效等。一切非角色嘴巴發出的聲音都歸在此管線。  
  - *角色聲音管線：* 包含角色的對話 TTS 語音與唱歌聲音，這類聲音需要同步角色的臉部表情與肢體動作，即屬於角色本體發出的聲音。

上述目標旨在提升系統的模組化與可維護性，並確保虛擬網紅系統中「背景／氣氛聲音」與「角色本體聲音」各自獨立又協調運作。

## 新的聲音播放架構概述
重構後的聲音系統將採用**前端驅動、後端指令**的架構。後端的責任是基於節目邏輯、互動事件等，生成一份包含所有要播放音效/語音的 **AudioTimeline 時間軸 JSON** 指令。前端接收此指令後，負責：

- 解析 JSON 中的聲音時間軸（例如每段音效/語音的開始時間、持續時間、類型等）。
- 根據系統現況（如目前已有的背景音、角色是否在講話等）驗證這些聲音事件是否可行或需要調整。
- 排程各個音效/語音的實際播放（包括串聯 Combo 音效、並行播放背景音樂與對話等），利用瀏覽器的 Web Audio API 或音訊庫（如 Tone.js）進行精準的時間控制。
- 確保不同管線的聲音互不衝突，例如角色講話時自動降低背景音量，或避免一次播放過多音效導致混亂。

在此架構下，**SoundEffectManager** 將專注於管理音效資源與基本行為，而 **AudioTimelineCoordinator**（聲音時間軸協調器）則負責根據後端提供的時間軸指令來協調前端的播放時序。兩者分工明確，並透過定義良好的 JSON 結構互相溝通。以下章節將詳細說明各個部分。

## 1. 基於時間軸的 AudioTimeline JSON 格式設計
首先，需要設計一個**以時間軸為基礎的 JSON 結構**來描述所有要播放的聲音事件。這份 AudioTimeline JSON 將作為後端輸出、前端輸入的橋梁。其核心是按時間先後定義聲音的播放資訊，包括：

- **開始時間 (startTime)：** 在整體時間線上此聲音事件開始的時間點。可以使用相對時間（相對於此次聲音播放序列的開始，例如用戶觸發互動的起始時刻視為 0）以秒為單位表示。也可以考慮使用毫秒或更精細的時間，但秒級別對大部分情境已足夠。
- **聲音類型 (type)：** 用於區分事件屬性。例如 `music`（背景音樂）、`sfx`（一般音效）、`combo`（組合音效起始點）、`tts`（文字轉語音對話）、`singing`（唱歌聲音）等。這有助於前端針對不同類型採取不同處理，例如對 `tts` 和 `singing` 觸發角色表情動畫管線。
- **資源標識 (resource)：** 指向實際聲音內容的標識方式。對於預先有的音效，可以是音效的唯一 ID 或名稱；對於 FreeSound 來的資源，可以是其 ID 以及對應的快取 URL；對於 Tone.js 合成音，可包含必要的參數（如合成器類型、頻率音高等配置）。如果是 TTS/唱歌，則可能為音檔的 URL 或一個代碼引用（由後端預先生成並存儲好音檔）。
- **持續時長 (duration)：** （可選）聲音長度，以秒為單位。如果音檔本身包含長度（例如背景音樂 MP3 的長度），可不明列，但對於 Tone.js 合成或未知長度的串接音效，提供 duration 能協助前端排程下一個事件開始時間。如果是 `combo` 類型，duration 可能表示整個組合的總長度或該組合內第一個音效的時長。
- **其他屬性：** 例如音量 (volume) 建議值、是否需要循環 (loop)、淡入淡出時間 (fadeIn/fadeOut) 等控制參數。尤其對背景音樂可能需要淡入淡出，對短音效則可直接播放。

AudioTimeline JSON 可以設計為**多軌道 (multi-track)** 的形式，以便同時描述音效管線與角色聲音管線。例如：

```json
{
  "timeline": [
    {
      "track": "sfx",
      "startTime": 0.0,
      "type": "music",
      "resource": "bgm_forest01",
      "loop": true,
      "volume": 0.8
    },
    {
      "track": "sfx",
      "startTime": 2.5,
      "type": "sfx",
      "resource": "door_open",
      "duration": 1.0
    },
    {
      "track": "sfx",
      "startTime": 4.0,
      "type": "combo",
      "resource": "combo_alert_sequence"
    },
    {
      "track": "voice",
      "startTime": 3.8,
      "type": "tts",
      "resource": "line_001",
      "text": "大家好，我是虛擬主播。",
      "duration": 2.2
    },
    {
      "track": "voice",
      "startTime": 10.0,
      "type": "singing",
      "resource": "song_intro_chorus",
      "duration": 5.5
    }
  ]
}
```

上述 JSON 範例說明：  

- `timeline` 為一陣列，包含按時間排序的事件。每個事件可附帶一個 `track` 或 `pipeline` 欄位來標示屬於音效 (`sfx`) 還是角色聲音 (`voice`) 管線（也可以考慮用兩個獨立陣列區分它們）。
- 第一個事件在 0 秒時開始播放背景音樂 `bgm_forest01`，會循環播放且音量預設 0.8。
- 第二個事件在 2.5 秒時播放一個名為 `door_open` 的音效，長度 1 秒（假設已知）。
- 第三個事件在 4.0 秒是一次 Combo 組合音效 `combo_alert_sequence`，它代表一串連續的警告聲音。此處未展開子細節，但前端收到這指令時會識別這是一組需要串行播放的音效（詳見下一節）。
- 第四個事件在 3.8 秒時開始播放角色的 TTS 對白（resource `line_001` 對應某預先合成的語音檔案）。同時提供 `text` 欄位供前端顯示或對照，duration 約為 2.2 秒。
- 第五個事件在 10 秒時為角色唱歌的聲音 `song_intro_chorus`，假設長約 5.5 秒。

透過上述時間軸，前端可以清楚知道在何時有哪種聲音事件發生。這個格式設計應力求**自描述**（self-contained）：即每個事件含足夠資訊讓前端能取得音源並播放。比如對 FreeSound 資源，`resource` 可設計成 `{id: 12345, url: "…", tier: 1}` 的物件，讓前端能直接使用 URL 播放或從 IndexedDB 快取獲取。

此外，設計時需考慮**時序精準度**：瀏覽器 Web Audio API 一般可以精確到幾毫秒內，但 JSON 用浮點秒數表示足矣。若有需要，也可以進一步允許 `startTime` 使用音樂節拍記號（例如 Tone.js 支援的 `"4n"`, `"8t"` 等），但除非系統對節奏有強依賴，否則不必複雜化。在此計畫中以秒計即可。

總之，AudioTimeline JSON 是整個重構的核心輸出格式，它清晰描述了**何時**播放**何種**聲音，以及相關參數，為前端執行提供了腳本依據。

## 2. Combo 音效串接邏輯與前端排程實現
**Combo** 指的是由多個音效組成的一系列串接效果（例如一個動作觸發連續的「砰-啪-隆」三段音效）。重構後，我們希望 Combo 的實現由前端來排程，確保串接順序精準且不會阻塞後端邏輯。

設計上，Combo 可以在 AudioTimeline JSON 中表示為一個特殊類型的事件（如上一節範例中的 `"type": "combo"`）。關鍵在於：

- 後端只需在 JSON 中標示 Combo 的識別碼或所包含的子音效列表，無需展開精確時序。例：「`resource`: "combo_alert_sequence"」即可對應前端某個已知的組合定義。
- 前端預先持有或能查詢該 Combo 的細節（例如在配置中定義 `combo_alert_sequence` 由三個音效 [alert1, alert2, alert3] 順序組成，各音效間隔固定 0.2 秒）。
- 當前端的 AudioTimelineCoordinator 遇到一個事件類型是 combo 時，便按照預定的模式**順序播放**其子音效。這可透過以下兩種方式實現：  
  1. **時間軸排程：** 前端在讀取 JSON 時，將 Combo 事件展開為多個子事件插入自己的播放時間軸中。例如 Combo 在 4.0 秒觸發，其中包含 alert1 長 0.5 秒、alert2 長 0.7 秒、alert3 長 1.0 秒（假設），則前端可在內部產生：4.0 秒播放 alert1，4.5 秒（4.0+0.5）播放 alert2，5.2 秒（4.5+0.7）播放 alert3。這種方式的優點是統一以時間軸處理，一旦展開就如同其他事件般調度。
  2. **事件驅動排程：** 不直接展開，而是在 4.0 秒觸發 Combo 事件時，先播放第一個音效 alert1，並在其播放結束的回呼（onended）中再啟動 alert2，如此鏈式串連。這種方式適合不知道精確持續時間的音效，可以確保上一段播放完再播下一段。

考慮到 Combo 定義通常固定且每段音效長度可預知，我們傾向採用**時間軸排程**。後端可提供每個組合音效的結構定義（可能在配置檔或資料庫中列出各 Combo 包含哪些音效及順序），前端在初始化時加載這些定義至內存中的一個字典。遇到 Combo 類型時，就依此自動展開為時間軸上的多個項目。若某段音效資源無法播放（資源缺失或未及時載入），前端可以記錄錯誤並嘗試跳過該子音效繼續後面的，確保整串不至於因單一失敗而中斷。

前端排程實現時，可以利用 Web Audio API 的精準計時功能或 Tone.js 提供的 Transport 機制來安排未來的播放。舉例而言：

- 若使用 Web Audio，前端在 4.0 秒準備播放 alert1 時，可以同時計算後續 alert2、alert3 的觸發時間，調用 `AudioBufferSourceNode.start(scheduledTime)` 在指定的未來時間點啟動它們，以達到精準串接而不受主執行緒延遲影響。
- 若使用 Tone.js，則可以利用 `Tone.now()` 獲取當前 AudioContext 時間，並調用 Tone.Transport 或直接用 `Tone.Player` 的 `start(time)` 方法，將後續音效調度在適當時間。例如：
  ```js
  const now = Tone.now();
  playerAlert1.start(now);
  playerAlert2.start(now + 0.5);
  playerAlert3.start(now + 1.2);
  ```
  這樣 alert2 和 alert3 會在指定延時後自動開始播放。

無論技術細節如何，關鍵是**前端掌握串接音效的節奏**。這意味著：

- 後端不需要等待一個音效播完再通知前端播下一個，減少通訊延遲和伺服器負擔。
- 串接完全在客戶端順序執行，更貼近即時性要求。
- 如有需要也可以在前端靈活調整間隔（例如未來做出 “節奏模式” 的互動，前端可以改變 Combo 音效間隔以配合節奏）。

## 3. SoundEffectManager 與 AudioTimelineCoordinator 模組職責分離
為了達成模組清晰分工，我們將重構 **SoundEffectManager** 並引入 **AudioTimelineCoordinator**，各自承擔不同責任：

- **SoundEffectManager（音效管理器）：**  
  - **資源管理：** SoundEffectManager 專注於音效資源本身的管理。例如載入音效檔案、存取 FreeSound 快取資源、管理 Tone.js 合成器實例等。它應維護一個音效庫（或資源池），使前端在需要播放某音效時可以快速取得對應的音訊資料（AudioBuffer 或音檔 URL 等）。  
  - **資源參數：** 管理每個音效預設的參數（如預設音量、分級 Tier 所屬、是否可同時多重播放等）。例如可限制同一音效在短時間內的重複播放次數，以避免聲音重疊失真。  
  - **（後端）ID 映射：** 如果 SoundEffectManager 在後端也有部分職能，它的責任是在接收到高階指令時將抽象的聲音代碼轉換為具體資源資訊。例如後端指令要求播放「laser_shot」，SoundEffectManager 知道這對應某個檔案 URL 或 FreeSound ID，並提前準備好該資源供前端取用。  
  - **（前端）播放介面：** 若 SoundEffectManager 也存在於前端（作為統一音效控制對象），則它提供簡潔的介面方法讓 AudioTimelineCoordinator 呼叫，如 `playSound(id, options)`、`playSynth(params)` 等，內部封裝實際調用 Audio API 或 Tone.js 的細節。

- **AudioTimelineCoordinator（聲音時間軸協調器）：**  
  - **時間軸解析：** 協調器模組負責接收後端傳來的 AudioTimeline JSON，並將其解析成前端可執行的播放計畫。它會依據事件的 `track`、`type` 進行分類處理：例如將 `track: "sfx"` 的事件交由音效管線處理，`track: "voice"` 的事件交由角色聲音管線處理。  
  - **播放調度：** 協調器根據時間軸對事件進行排序（通常後端已排序好，但仍需檢查是否有時間衝突），然後設定計時器或使用音訊時鐘在正確的時間觸發每個事件。它就像一個導播，時間一到就調用對應的播放函數。  
  - **衝突處理：** 當時間軸上可能存在衝突或資源不可用情況時，協調器需要即時處理。例如兩段背景音樂事件重疊，或角色在講話時又有另一段講話事件到來。協調器可根據預定策略暫停、取消或延後某些事件。這些策略可配置，例如：「永遠只允許一個 voice 管線事件同時播放」，則當新的 voice 事件來臨時，如果上一段語音尚未結束，可以選擇打斷前一段或忽略新的——具體取決於產品需求，並在協調器中實現。  
  - **通知與回呼：** 協調器可在重要節點（如一段音頻播放結束、一組 Combo 完成）時發出通知給系統其他部分。例如通知角色表情控制模組「這句對白已播完」，或者通知劇情邏輯「這個音效已播放完畢」以觸發後續流程。這些通知可透過事件機制或 Promise/Callback 提供給上層使用。  
  - **UI 互動：** 儘管後端不處理 UI，協調器在前端可以配合 UI 做出一些反應。例如當播放某段音樂時，UI 上顯示音符圖示，或背景舞台燈光隨音樂節奏閃爍。協調器在解析 JSON 時可以將這類資訊（如果 JSON 有提供提示）傳給 UI 控制模組。

透過上述分離，SoundEffectManager 主要處理「素材層面」，AudioTimelineCoordinator 處理「時序層面」。兩者透過明確的介面協作：協調器在某個時間需要播放某音效時，就調用 SoundEffectManager 提供的方法執行。SoundEffectManager 可以回傳一個播放實體（例如 AudioBufferSourceNode 或 Tone.Player 對象）以供協調器追蹤其進度或監聽結束事件。這種解耦方式讓我們將來即使更換底層音訊庫（例如改用不同的 TTS 服務或音效引擎），大部分時間軸調度邏輯可以保持不變，反之亦然。

## 4. FreeSound 音效資源分級（Tier‑0/1/2）與快取策略
FreeSound 提供大量免費音效，但下載與解析音效檔案需要時間。為了在保證即時性的前提下善用 FreeSound 資源，我們引入**資源分級**與**快取**的概念，將音效資源按使用頻率、檔案大小和重要程度劃分為三個等級：

- **Tier-0（零級）：** 關鍵即時資源。本地內建或隨應用預載的音效，**不允許有延遲**。例如常用的 UI 點擊音、錯誤提示音，或主要背景音樂片段等。這些音效應該打包在前端應用中，或在首次載入時就快取完畢。SoundEffectManager 對 Tier-0 資源可以在初始化時就載入至內存（AudioBuffer）或確保對應 `<audio>` 元素已可立即播放。

- **Tier-1（一級）：** 高頻使用或中等大小資源。此類資源可能不是每次啟動都用到，但使用頻率較高，且檔案大小適中。我們可以在應用啟動後的空檔**預取**（prefetch），或者在第一次使用後將其快取至本地（如 IndexedDB）。例如角色常用的口頭禪音效、部分環境背景聲（風雨聲、街道噪音等）。SoundEffectManager 可以在後端維護這些資源的清單，前端啟動時檢查快取，如無則閒置時提前下載。對 Tier-1 資源採用“用過一次後留在快取”的策略，下次使用時即時可調用。

- **Tier-2（二級）：** 低頻或大型資源。不常用的音效，或者體積很大的音樂/音頻檔案（例如罕見事件的特殊音效，或完整歌曲文件）。這些資源不會預先下載，只有當時間軸指令明確要求播放時才臨時抓取。SoundEffectManager 對 Tier-2 資源的處理是**延後載入**：前端在接到播放指令時，若發現所需資源不在快取，才即時向伺服器或 CDN 請求。在播放前可能需要稍微延遲或顯示載入提示。如果 Tier-2 資源下載後有可能重用，也可以考慮下載完後存入快取，但應設定快取上限或淘汰策略（例如快取總大小超過某值就移除最久未使用的 Tier-2 資源）。

為配合以上策略，後端需要：

- 為每個音效資源標註其 Tier 級別（可在資料庫或配置中維護）。
- 提供一個音效資源 API，讓前端能請求資源。比如前端發現音效未快取，則調用 `GET /sound_resource/{id}` 取得音檔，後端回傳該音檔或其 CDN URL。
- 實現基本的快取通知機制：例如前端在載入完資源後通知後端，以便後端更新資源使用頻率，必要時調整 Tier 分級或預載清單。

前端的 SoundEffectManager 則需要：

- 初始化時載入 Tier-0 資源。
- 背景預取 Tier-1 清單中的資源（在應用初始或空閒時進行，避免影響使用者互動）。
- 提供查詢介面檢查資源可用性（例如 `isResourceAvailable(id)`），以便 AudioTimelineCoordinator 在排程時決定是直接播放還是需要先等待下載完成。
- 使用瀏覽器可用的存儲機制保存快取，如 IndexedDB（二進位大型檔案存取）或 Cache API。由於音檔可能較大，不建議使用 localStorage（容量有限且同步阻塞）。
- 針對 Tier-2 資源，如果時間軸指令要求立即播放，則在排程時採取特殊處理：要麼嘗試快速下載並稍後開始播放，要麼在時間軸上稍微延後該事件直到資源到位再播放（必要時搭配載入動畫提示），但需注意與其他事件的時間協調以免不一致。

透過分級管理，我們確保常用音效快速響應，同時仍能在需要時動態調用大量外部音源而不阻塞系統。這種快取策略能減輕網路延遲對使用者體驗的影響，也降低重複下載的頻率。

## 5. 後端職責：輸出結構化指令（不處理播放與排程）
重構後，後端在聲音播放流程中的職責將更聚焦於**邏輯決策與指令生成**，而非實際播放控制。具體來說：

- **場景邏輯決策：** 後端基於劇本、使用者互動或 AI 判斷，決定何時需要播放哪些聲音效果或語音。例如偵測到聊天室指令要求角色播放笑聲效果，或 AI 判定角色此時應說一句話。
- **生成 AudioTimeline 指令：** 後端將上述決策結果轉換為結構化的 AudioTimeline JSON，包含在一段時間內需要播放的所有聲音事件。例如角色開始說話的同時，可能需要降低背景音樂音量和播放一個提示音效，這些都可以一起在 JSON 中描述（如在 0 秒安排 voice 事件，同時在 0 秒安排一個背景音量調整事件）。
- **不直接控制播放：** 後端不做音訊串流或播放控制，不會有「延遲 X 秒後再播放某音效」這類細節操作，一切精準時序交給前端處理。後端在指令中只需提供相對時間，無需精準對齊真實時鐘。即使後端處理稍有延遲，前端接到指令後仍可基於自身時鐘校準執行。
- **資源準備：** 後端需確保在發出播放指令前，相應的音效/語音資源已經準備好供前端獲取。特別是 TTS 語音音檔和唱歌音檔通常由後端生成或轉碼。因此在把 voice 類事件放入時間軸前，後端應已拿到對應的音檔（例如調用 TTS 引擎得到 mp3），並將其存放在前端可訪問的 URL。對於涉及 FreeSound 的音效，如果尚未快取，也應該提前觸發後端下載或確認已有可用連結。總之，後端輸出的 JSON 應盡量指向「已準備好」的音源，以免前端收到指令卻找不到資源可播。
- **指令簡潔與狀態最小化：** 後端不維護前端播放的狀態細節（一旦指令送出，由前端接管執行）。如果一系列聲音需要分段下達，後端可以多次發送 JSON，但理想情況下，能合併的就合併，減少通訊頻次。例如角色要說一長段話，後端可以一口氣將其拆成多個句子的 voice 事件（附帶表情同步資訊）以及所需背景音處理，一起打包成一份時間軸指令發送。

後端重構的重點在於**邏輯清晰**：擺脫以往可能混雜著播放延時或音效串接的實作，把注意力放在「**決定播放什麼**」以及「**大概什麼時間**」。如此一來，後端程式碼更容易維護（因為不涉入音效裝置或瀏覽器計時等繁瑣細節），也更容易測試（輸入觸發條件，檢查輸出 JSON 是否正確）。為了輔助調試，後端還可以記錄每次輸出的 AudioTimeline JSON 作為日誌，以便對照前端的實際播放行為進行驗證。如果發現不符預期，可重播相同 JSON 在測試環境中還原問題，快速定位前後端協作的任何瑕疵。

## 6. 唱歌模組與既有 TTS 播放流程的拆分與共享表情管線
目前角色的語音播放流程主要針對 TTS（文字轉語音）對話。而引入唱歌功能後，需要在架構上將兩種語音來源適當拆分，又能共用角色表情/動作同步的處理管線。

**拆分方面：**

- **TTS 模組：** 專職處理角色的對話語音。通常流程為：後端接收到角色要說的文字 -> 調用 TTS 引擎取得合成語音音檔 -> 將該音檔路徑和時間軸事件返回前端 -> 前端根據時間軸播放，並同步角色嘴型表情。
- **唱歌模組：** 處理角色的唱歌聲音。唱歌的來源可能與 TTS 不同（可能是預先錄製的音檔，或透過歌聲合成引擎生成）。它可能需要處理完整歌曲的歌詞時間點、節拍資訊等，以便同步嘴型和表演動作。例如一段唱歌音檔對應的逐字歌詞字幕，以及每個字/音節的時間戳。唱歌模組在後端會負責準備這些資料（可能包含一份類似卡拉 OK 的字幕時間標記 JSON）。
- **資源取得：** TTS 語音一般是即時生成即時播放，而唱歌音檔通常較長，可能需要預先處理或載入。因此在使用時間軸安排上，唱歌事件最好在實際播放前就已經有對應的音檔準備就緒（可以讓使用者提前選歌，系統先行生成或載入音檔）。

**共享方面：**

- 無論 TTS 還是唱歌，角色嘴巴的動作（口型開合、發音嘴形 viseme）、表情變化以及肢體動作都需要跟隨聲音內容同步。為此，可設計一個**共用的表情/動作同步管線**。做法是讓 TTS 模組與唱歌模組在後端生成語音時，同時生成或提供對應的 **語素/嘴形時間標記**（phoneme timings）或至少句子/字詞的節奏點：
  - 對 TTS，如果所用的 TTS 引擎支援，通常能返回每個音素或字的時間資訊；否則可以在前端透過分析音量波形近似推斷說話節奏（但精準度較低）。理想情況是取得具體的音素-時間資料，以便前端做出精準的嘴形同步。
  - 對唱歌，如果是預錄音檔，可以在離線階段對音檔進行分析，得到歌詞每個字在音檔中的時間位置；如果是歌聲合成，也可以在生成時輸出對應的時間標記。若是固定歌曲甚至可由人工校對製作時間標記檔。
- 前端的虛擬主播動畫系統只需要認一種統一的資料格式，例如一個按照時間排序的**嘴形/表情隊列**：`[ {time: 0.1, mouth: "O"}, {time: 0.2, mouth: "A"}, ... ]`。如此一來，無論該隊列來自 TTS 或唱歌，前端動畫模組都可以逐項讀取並在對應時間驅動角色的嘴型與表情變化。
- 為達成上面這點，可以定義**語音同步數據結構**（例如 VoiceCue）。其中包含語音音檔資訊以及嘴形/表情同步資訊。例如：  
  ```json
  {
    "audioUrl": "voices/line_001.mp3",
    "visemes": [
       {"time": 0.0, "mouth": "closed"},
       {"time": 0.1, "mouth": "O"},
       {"time": 0.2, "mouth": "A"},
       ...
    ]
  }
  ```  
  對於唱歌，同樣的結構但 visemes 列表可能更密集，甚至可以加入音高資訊供肢體動畫參考（例如角色在高音部分張大雙臂等特定動作）。
- 在 AudioTimeline JSON 裡，對於 `tts` 和 `singing` 類型的事件，可以加入一個欄位引用上述同步數據或者直接嵌入 viseme 列表。例如：  
  ```json
  {
    "track": "voice",
    "startTime": 3.8,
    "type": "tts",
    "resource": "line_001",
    "duration": 2.2,
    "visemeData": [ ... 如上所示 ... ]
  }
  ```  
  這樣前端在播放語音對白的同時，將 `visemeData` 丟給 Avatar 表情模組去驅動角色的嘴型動畫。
- 此外，角色說話和唱歌在動作表現上可能有所區別：唱歌時肢體可能隨節拍舞動，而普通對話則較靜態。可以擴充同步數據的格式，加入節拍或情緒標記，供前端的肢體動畫模組使用（例如每小節或每強拍觸發一次揮手動作）。TTS 對話一般只需嘴型和細微表情，而唱歌可以有更豐富的舞台動作，這部分都可以通過在聲音事件中添加對應的動畫線索來實現。

透過模組拆分，我們可以各自優化 TTS 與唱歌流程：TTS 模組側重降低延遲、提高語音自然度；唱歌模組側重音準、節奏和表演效果。兩者的輸出通過統一的同步資料格式讓前端動畫系統處理，確保角色無論說話還是唱歌，嘴型表情和動作都能精準匹配聲音。

## 7. 「背景／氣氛」與「角色本體」聲音分管設計
最後，我們看看整體設計如何滿足虛擬網紅系統中**背景/氣氛聲音**與**角色本體聲音**區分的需求。重構後採用的雙管線體系，正對應這兩大類聲音：

- **背景/氣氛聲音管線（Sound Effects Pipeline）：** 處理一切非角色直接發出的聲音，包括環境背景聲（風聲、環境音樂）、效果音（按鈕音、爆炸聲等）以及氛圍渲染音效（觀眾歡呼、迴音效果等）。這個管線可視作「場景聲音」來源。透過將背景音效獨立一條管線，我們可以對其集中控制：  
  - **獨立音量控制：** 使用者或系統可單獨調整背景音量而不影響角色聲音，確保角色講話時語音清晰突出。  
  - **混音管理：** 在前端我們可以將背景音效送入一個獨立的 AudioContext 或其下的 Audio Node（音效節點），方便對整體做效果處理（例如加一點混響讓環境音更真實，或在角色講話時降低其增益做到 ducking）。  
  - **時序獨立：** 背景聲音通常是持續或循環的，角色聲音則是間歇的。透過時間軸區分，角色不講話時背景音樂可持續播放而無需特殊處理；角色講話開始時，若需降低背景音（ducking），協調器可以在角色 voice 事件來臨前插入一個背景音量調整事件到背景管線中，實現平滑過渡。  
  - **多來源統一：** 由於背景管線涵蓋多種來源（本地音檔、FreeSound下載、Tone.js 合成等），SoundEffectManager 在此扮演關鍵角色來統一介面，對 AudioTimelineCoordinator 而言，不論聲音來源如何，調用方式都一致（例如皆可視為 `playSound(resource, time)` ，內部會自適應使用 AudioBuffer 播放或調用 Tone 合成）。

- **角色本體聲音管線（Voice Pipeline）：** 專門處理角色自身的語音輸出，包括對話 TTS 和唱歌兩類。這條管線直接關聯角色的嘴型表情和動作：  
  - **單一聲源原則：** 角色聲音一般不會同時有兩段重疊（角色不可能同時說話和唱歌）。前端協調器將確保不會並行播放多個 voice 事件。如有新語音到來會按照定義的策略處理（例如等待上一個結束或中斷上一個）。此外，系統可提供對角色聲音的全局開關（例如緊急靜音角色聲音，但保留背景音，用於特殊情況或開發調試）。  
  - **動畫同步：** 如前述，voice 管線每播放一段語音，都會將對應的 viseme/表情資料送給動畫模組。Voice 管線需要在播放開始時通知動畫開始對嘴同步，在播放結束時通知動畫恢復空閒表情或切換到下一段動畫狀態。這可在 AudioTimelineCoordinator 內對 voice 事件做鉤子處理來實現。  
  - **音質與效果：** 角色語音要求清晰、穩定，通常不對其添加特殊效果（除非劇情需要，如一段電話聲音加濾波效果）。可以在 voice 管線的 AudioContext 上預設一些基礎處理，例如 EQ 均衡或限幅器，避免語音過尖或失真。同時，因為 voice 管線獨立，我們對其進行處理時不會影響背景管線。  
  - **與背景聯動：** 當角色聲音出現時，往往需要與背景聲音聯動協調。典型例子是**自動降音 (ducking)**：讓角色講話時背景音樂音量自動降低，講完後恢復。這可以透過協調器在時間軸上實現——在角色 voice 事件開始時插入對背景音量的降低操作事件，在 voice 結束時再插入提高音量的事件，或直接利用 Web Audio 動態調整兩條管線的增益實現平滑 ducking 效果。

**整體而言**，雙管線的設計賦予我們對「背景/氣氛」與「角色本體」聲音各自獨立處理又互相協調的能力。開發上，不同模組各司其職：音效設計/處理專注於背景管線，語音合成/動畫專注於角色管線，互不干擾。效能方面，瀏覽器可同時處理多個 AudioContext 或多音源播放，我們亦可針對不同聲音類型優化（如背景音樂可預解碼緩衝、角色語音著重低延遲）。最終，觀眾將體驗到更平衡而豐富的聲效效果：有環繞的背景氛圍，又能清晰聽見角色對話與歌聲，兩者相得益彰。

## 結論
此重構計畫旨在為 space_live_project 的聲音系統建立一個穩健、易擴充的架構。透過明確區分音效與角色聲音兩大模組、前端主導聲音播放流程，以及精心設計的 AudioTimeline 時間軸協調機制，我們能讓系統在處理複雜音效場景時保持井然有序。此外，引入 FreeSound 資源的分級快取策略將改善音效載入速度，唱歌與對話聲音管線的拆分則為未來更多角色表現形式奠定基礎。

這份計畫書詳細列出了重構所需考慮的各個方面，從資料格式、模組劃分到資源管理和動畫同步，均有具體方案。實施此重構後，預期可以達到：

- 聲音相關程式碼的可讀性與維護性大幅提升，各功能模組邏輯清晰分明。
- 新增音效或語音類型（例如添加新的音效資源來源，或不同風格的 TTS 引擎）將更為容易，因為只需在對應模組中擴充即可，無須改動整體架構。
- 使用者體驗提升，音效與語音配合更加流暢，減少不同步或資源延遲導致的突兀情況。
