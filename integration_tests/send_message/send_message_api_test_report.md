# Send Message API 整合測試報告

## API 概述
**端點**: `POST /api/control/send-message`  
**功能**: 透過 WebSocket 向前端發送聊天訊息，支援 TTS 語音合成

## 測試範圍

### 基礎功能測試 ✅
- **基本文字訊息發送**: 成功發送並接收回應
- **長文字訊息處理**: 能夠處理較長的文字內容
- **不同訊息類型**: 支援 `chat-message`, `system-message`, `notification`, `announcement`
- **特殊字符和多語言**: 完美支援中文、英文、特殊符號和 emoji
- **空內容處理**: 能夠處理空字符串和僅包含空白字符的內容
- **預設值處理**: 未指定 `message_type` 時正確使用預設值 `chat-message`

### 進階功能測試 ✅

#### 1. TTS 整合功能
- **語音合成**: 成功為文字內容生成語音檔案
- **音頻 URL 生成**: 每條訊息都生成對應的音頻 URL
- **WebSocket 廣播**: 訊息和音頻 URL 正確透過 WebSocket 傳送

#### 2. WebSocket 訊息格式驗證
- **頂層結構**: 包含必要的 `type` 和 `message` 欄位
- **訊息物件**: 包含完整的訊息欄位
  - `id`: 格式為 `api-bot-{timestamp}`
  - `role`: 固定為 `"bot"`
  - `content`: 正確的訊息內容
  - `timestamp`: ISO 格式時間戳
  - `isFromAPI`: 標記為 `true`
  - `audioUrl`: TTS 生成的音頻檔案路徑

#### 3. 不同長度內容的 TTS 處理
- **短文字** (2 字符): 處理時間 ~2.9 秒，成功生成音頻
- **中等文字** (31 字符): 處理時間 ~4.2 秒，成功生成音頻  
- **長文字** (98 字符): 處理時間 ~9.0 秒，成功生成音頻
- **處理時間**: 隨內容長度線性增長，符合預期

#### 4. 訊息時序和延遲分析
- **API 回應時間**: 1.3-1.9 秒
- **WebSocket 延遲**: 與 API 回應時間相當
- **併發處理**: 支援多個並發請求，成功率 100%

### 錯誤處理測試 ✅
- **無效 JSON**: 正確返回 422 狀態碼
- **缺少必要欄位**: 正確返回 422 狀態碼並提供詳細錯誤信息
- **連接檢查**: 會檢查前端連接狀態

## API 參數

### 請求參數
```json
{
  "content": "訊息內容",
  "message_type": "chat-message"  // 可選，預設為 "chat-message"
}
```

### 回應格式
```json
{
  "success": true,
  "message": "消息已發送到前端", 
  "connections": 1
}
```

## WebSocket 訊息格式

### 發送給前端的格式
```json
{
  "type": "chat-message",
  "message": {
    "id": "api-bot-21513575",
    "role": "bot",
    "content": "你好！這是一個測試訊息。",
    "timestamp": "2025-06-03T08:21:15.896584",
    "audioUrl": "/audio-file/b9a61ccb8a.mp3",
    "isFromAPI": true
  }
}
```

## 技術特性

### TTS 整合
- **引擎**: 整合現有的 TTS 服務
- **音頻格式**: MP3 格式
- **檔案管理**: 自動生成唯一檔名並保存到 `/audio-file/` 目錄
- **URL 生成**: 生成相對路徑的音頻 URL

### WebSocket 廣播
- **連接管理**: 使用現有的 `ConnectionManager`
- **訊息格式**: JSON 格式的結構化訊息
- **廣播機制**: 向所有活動連接廣播

### 錯誤處理
- **連接檢查**: 在處理前檢查是否有活動連接
- **TTS 失敗處理**: 即使 TTS 失敗也能發送文字訊息
- **例外處理**: 完整的錯誤捕獲和回應

## 已知問題

### 音頻 URL 路徑問題
- **問題**: 音頻 URL 使用相對路徑格式 `/audio-file/xxx.mp3`
- **影響**: 直接 HTTP 請求該 URL 會失敗
- **建議**: 前端應該加上完整的基礎 URL 來訪問音頻檔案
